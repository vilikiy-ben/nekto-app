# Архитектура

```
┌──────────────── Nekto.app (SwiftUI, macOS 15+) ────────────────┐
│ Onboarding (знакомство ─► Installer ─► папка) ─► Shell (история · лента · «Скрыто»)
│                                   │
│ AppModel ── Composer (строка ввода)       Store ── рабочая папка/.nekto
│    └─ Pipeline: очередь → EngineClient ◄─► движок (JSON-lines, stdin/stdout)
│                                   ▼
│        sandbox-exec (сеть запрещена) → python -m nekto_engine
│ Vision OCR / PDFKit / NSAttributedString: PDF, сканы, картинки, RTF/DOC/ODT → текст
└─────────────────────────────────────────────────────────────────┘
~/Library/Application Support/Nekto/   — только среда и модель
  runtime/python, runtime/venv, model/ea7610b/ (+ mapped/ — веса отдельным файлом), state.json
```

## Имя приложения
Имя записано в трёх местах: `App/Sources/App/Brand.swift` (интерфейс, пути, ключи настроек — `Brand`, `Footprint.current`),
`App/project.yml` (цель, продукт, идентификатор `app.nekto.mac`) и `scripts/brand.sh` (скрипты). Проверка — `scripts/checks/name-audit.py`.

## Онбординг
Поток шагов — `Onboarding/OnboardingFlow.swift` (`OnboardingStep`): шаги 1, 2, 3а — внутри фазы `.welcome`
(`AppModel.welcomePage`), 3б — фаза `.setup`, 4 — `.ready`, пока папок нет (`needsFolder`). `RootView` держит онбординг
одной веткой (`inOnboarding`), поэтому вид и сцена не пересоздаются при смене фазы. «Установить» — `startSetup()`;
после установки приложение само переходит к шагу 4. Выбор папки — `FolderChoice`: панель `WorkFolders.choose`
ничего не добавляет, папку добавляет «Начать работу» (`addFolder` / `useSuggestedFolder`).

### Сцены онбординга
Сцены нарисованы «пером» на JS (`App/Onboarding/`: перо `ink/`, сцены `scenes/`, плеер `preview/player.js`) и
показываются на `<canvas>` в `WKWebView`.

- **Страница.** `App/Onboarding/app/scene.html` + `scene.js`: одна сцена на весь вид, `ScenePlayer` из
  `preview/player.js`. Управление — `nekto.set({ scene, state, theme, still, playing, fps })`; новая сцена или
  состояние появляются растворением поверх прежней. До первого кадра страница прозрачна.
- **В бандл** — фаза сборки в `App/project.yml` вызывает `scripts/embed-onboarding.sh`: он идёт по `import … from` от
  страницы и копирует в `Nekto.app/Contents/Resources/Onboarding/` то, что она импортирует (16 файлов, ~130 КБ).
  Пропавший импорт ломает сборку. Подпись бандла — после (в `embed-engine.sh`).
- **Загрузка** — `SceneView.swift`. Не `loadFileURL`: страница — ES-модули, а модули с `file://` WebKit не грузит
  (у file:// нет источника, импорт блокируется как запрос к чужому; проверено в WKWebView). Поэтому `SceneFiles`
  (`WKURLSchemeHandler`) отдаёт файлы папки `Onboarding` по схеме `nekto-scene://scene/…`. Песочницы App Sandbox
  у приложения нет (entitlements пусты, Hardened Runtime), дополнительных прав WKWebView не понадобилось.
- **Без сети.** CSP страницы: `default-src 'none'; script-src 'self'` — только скрипты своей схемы; навигация на
  любую другую схему отменяется; `websiteDataStore = .nonPersistent()` — ничего не пишется на диск.
- **Что передаёт Swift.** Сцена шага; у монолита `progress` — 0 до установки, во время — `Installer.overall`,
  округлённый до десятых (новое состояние — когда ложится слой); тема — `colorScheme` окна (настройка «Оформление»,
  а не тема системы); `still` — «Уменьшить движение» (кадр 0); `playing` — окно на экране (`occlusionState`).
  Потолок 60 кадров в секунду (`SceneHost.frameRate`).
- **Ресурсы.** Окно закрыто другими или свёрнуто — кадры не рисуются (и сам WebKit останавливает
  `requestAnimationFrame`). После онбординга `SceneView` убирается, `SceneHost.tearDown` снимает обработчик
  сообщений, процесс WebContent завершается.

## Рабочая папка
Всё, что пользователь обработал, лежит в выбранных им папках (первая по умолчанию `~/Documents/Nekto`).
Папок может быть несколько; `WorkFolders` хранит их список, текущую папку для новых обработок и свёрнутые:

```
Рабочая папка/
  2026-11-21 Трудовой договор [ФИО_1]/        ← результаты одной обработки
    Трудовой договор [ФИО_1] (обезличено).docx
    Текст (обезличено).txt
    Ответ нейросети (с данными).txt
  .nekto/                                  ← скрытая история
    README.txt
    <id>/processing.json                       ← заголовок, документы, режимы, таблица меток, состояние движка
    <id>/items/<id>/source/<исходный файл>     ← копия входа (для пересчёта после правок)
    <id>/items/<id>/text.txt                   ← вставленный текст или распознанный скан
    <id>/items/<id>/preview.txt                ← что копируется в чат («Скопировать»)
    <id>/items/<id>/layout.json                ← вид документа в ленте и редакторе (DocumentLayout)
```

Имена папок обработок и заголовки в истории берутся из обезличенного результата, поэтому в них
нет ПДн. Таблица меток с исходными значениями хранится только в `.nekto`. Но восстановленный ответ нейросети
(`… (с данными).txt`, `AppModel+Pipeline`) ложится в ту же папку результатов, что и обезличенные файлы, поэтому
в чат уходят файлы, а не папка целиком. Папки запоминаются закладками (`WorkFolders`), так что переименование
или перенос в Finder не теряет историю. Модули: `Library/WorkFolders`, `Library/Store`, `Library/Processing`.

## Обработка
Обработка — строка истории, аналог чата. Внутри документы, тексты и ответы нейросети с общими
метками. В движке ей соответствует своя сессия (`session` = id обработки).

1. **Отправка** (`AppModel+Pipeline.send`): файлы и текст из строки ввода становятся заданиями.
   Текст с метками этой обработки (или с включённым режимом «Ответ нейросети») — ответ нейросети.
2. **Импорт.** По UTType решаем, кто читает файл: движок (текст, таблицы, OOXML, JSON, разметка, почта)
   или Swift (PDF, изображения, RTF/DOC/ODT → извлечённый текст → `clean_text`). Копия входа — в `.nekto`.
3. **Сессия движка.** Перед первым заданием обработки после запуска приложение поднимает её
   из `processing.json` (`restore`) и передаёт режимы (`configure`). После каждой операции движок
   возвращает `state`, приложение сохраняет его.
4. **Детектор** (`detector.py`) сводит три независимых источника. Модель — один голос, а не судья: на жаргоне,
   опечатках и аббревиатурах она уверенно ошибается, поэтому решение принимается по всем свидетельствам вместе:
   - модель (`model/`): токен-классификатор `rubert-base-pii-ner` на ONNX Runtime отдаёт слова с метками и уверенностью
     и ничего не решает. Сплошной текст читает окнами из соседних строк, ячейки таблиц — по отдельности; текст,
     где ей нечего найти, не читает вовсе (ворота), ответы помнит по тексту окна;
   - имена (`names/`): `lexicon` — что слово значит само по себе, `finder` — ФИО по словарю, регистру, соседям,
     словам документа и модели вместе, `mention` — роли и согласованная начальная форма, `registry` — кто есть кто;
   - остальное: `entities` собирает контакты, номера и адреса из меток модели и проверяет форму, `fields` читает поля
     анкеты «Метка: значение» (метки — `labels.py`, общие с заголовками столбцов), `rules` — номера, ссылки, секреты, даты;
   - организации (`orgs.py`) — только в режиме «Скрывать организации» (`configure hide`): у модели нет такого класса.
   **Вторая сеть** (`recall.py`): проверенное однажды — везде (фамилия в других падежах, номер точным совпадением),
   авторы реплик, учётные записи по найденной почте и по фамилии найденного человека латиницей. Таблицы любого
   формата, в том числе вставленные в текст (табуляция, Markdown, «;», « | », вывод `psql`): короткие ячейки строки —
   вместе, длинные — сами по себе, строка — своя область склейки людей (`formats/rows.py`). **Сессия** (`session.py`): метка на значение; люди привязываются
   к меткам по всему документу сразу (`bind`).
5. **Результат** движок пишет во временную `staging/`, приложение переносит файл в папку обработки
   (пересчёт заменяет прежний файл). Вместе с файлом движок отдаёт два представления: `layout` — вид документа
   для человека (блоки: таблицы, слайды, листы, поля письма, колонтитулы, примечания, свойства файла;
   `formats/layout.py`) и `preview` — текст для «Скопировать» (файл как есть или Markdown из тех же блоков).
6. **Восстановление** — в Swift (`Library/Restorer`): метки из ответа → исходные значения из таблицы обработки.

Правки (скрыть пропущенное, не скрывать ложное) и режимы («Оставить даты», «Оставить ссылки», «Скрывать организации»)
действуют на всю обработку: решение записывается сразу (`Processing.desired`, `modes`) и видно в том же кадре
(`Library/Review`), затем по одной уходит движку (`AppModel+Edits`), и документы пересчитываются — открытый первым.
Модель при пересчёте не запускается: движок помнит находки по отпечатку текста (`Detector._cache`).
Документ, который закрытие приложения застало посреди пересчёта, помечен в истории (`stale`) и пересчитывается сразу после запуска.

## Протокол движка
См. docstring `Engine/nekto_engine/server.py`. Без сессии: `load`, `selftest`, `ping`, `cancel`.
С полем `session`: `clean_text`, `clean_file`, `force`/`unforce`, `allow`/`unallow`, `configure`,
`restore`, `drop`, `mapping`, `reset`. События: `hello`, `progress`, `result`, `error`.
`clean_file` и `clean_text` возвращают `layout` — `{version, blocks}` или `null` (тогда приложение показывает текст).

## Интерфейс
`Workspace/ShellView` — каркас: `Sidebar` (история), центр (`HomeView` / `FeedView` / `ReaderView`),
`Review/InspectorView` («Скрыто», только в редакторе: группы `ReviewGroupHeader`, строки `ReviewEntryRow`, фильтр `ReviewFilterBar`; модель — `Library/Review`, память — `Library/ReviewPreferences`, массовые решения и ⌘Z — `AppModel+Review`), `Settings/SettingsView` (место `.settings` в том же окне). Верхняя полоса — системная панель инструментов без фона: «светофор»
по её центру, кнопки панелей и стрелки ‹ › — её элементы. Строка ввода — `ComposerView`
(поле `ComposerField` на NSTextView; прикреплённые файлы — плитки в той же строке, она растёт вверх), под ней на главном экране подсказки `ActionList`. Документ с метками — `DocumentView`
(`Workspace/Canvas`): свой движок вида вместо NSTextView. `Document/`: модель `DocumentLayout` (из движка или из Markdown
ответа нейросети, `MarkdownLayout`); `Document/Scene` раскладывает её в фоне в сцену — полосы (абзацы, строки таблиц),
куски текста на CoreText, подложки слайдов и кода — с кешем по кускам (`SceneBuilder`, `TextLayoutCache`);
`DocumentCanvasView` рисует только видимые полосы и даёт выделение, ⌘F (`NSTextFinder`), меню, ⌥ и шапку таблицы сверху.
Почему не NSTextView: TextKit ищет, что рисовать, по строкам текста, а строки таблицы идут не по возрастанию высоты —
на больших листах часть полос оставалась пустой; свой движок рисует полосы, монотонные по построению. Проверка без
приложения — `scripts/checks/document-check.sh`. Имена значков — `iconName` (`Design/Components`): подсказку получают
только значки без общепринятого смысла; обучение один раз — `Design/Teaching` (TipKit).

## Разработка и проверка

Сборка и тесты — раздел «Сборка из исходников» в `README.md`. Что ещё есть:

| Команда | Что проверяет |
|---|---|
| `scripts/test-engine.sh [аргументы pytest]` | тесты движка в той же песочнице без сети, что у приложения; модель — `scripts/fetch-model.sh` |
| `scripts/checks/document-check.sh [--png <папка>]` | вид документа и движок редактора без приложения: JSON, Markdown, раскладка таблиц, полнота отрисовки, скорость кадра |
| `scripts/checks/name-audit.py` | имя приложения согласовано в трёх местах |
| `scripts/checks/repo-hygiene.py` | в репозитории только продукт; перед каждым коммитом после `git config core.hooksPath .githooks` и в CI |
| `scripts/checks/commit-identity.py` | автор назван явно, а не собран git из учётной записи Mac (`имя@имя-компьютера`); в сообщениях нет соавторства ИИ-ассистента; перед коммитом и перед пушем |
| `scripts/checks/home-paths.sh <Nekto.app>` | в сборке нет путей домашней папки; запускает `build.sh` после каждой сборки |

Хуки включаются один раз в клоне: `git config core.hooksPath .githooks` — `pre-commit` (две первые проверки
выше), `commit-msg` (сообщение без соавторства ИИ-ассистента) и `pre-push` (адреса и сообщения всех уходящих
коммитов: ловит rebase, cherry-pick и `--no-verify`). Чтобы git нигде
не подставлял автора сам: `git config --global user.useConfigOnly true`.

CI (`.github/workflows/engine.yml`) повторяет на macOS путь из чистого клона: `dev-runtime.sh` → `fetch-model.sh` →
`test-engine.sh` → `name-audit.py`.

Отладочные аргументы запуска (`-NektoFolder`, `-NektoOpen`, `-NektoAttach`, `-NektoOnboarding` и другие) открывают
нужный экран без кликов — список в `App/Sources/App/DebugScenario.swift`. Работают только в Debug-сборке: ключи
читаются через `DebugDefaults`, который в выпуске пуст.

## Выпуск

`scripts/build.sh --dmg` — ad-hoc-сборка для себя. Release проходит strip (`App/project.yml`): иначе карта отладки
оставляет в исполняемом файле пути исходников с машины сборки; символы для разбора падений — в `Nekto.app.dSYM`
рядом со сборкой в `build/DerivedData.noindex`. `scripts/release.sh` — выпуск для раздачи: подпись Developer ID,
Hardened Runtime, нотаризация приложения и образа, билеты вшиты (`stapler`), итог — `dist/Nekto-<версия>-<сборка>.dmg`.
Один раз на Mac выпуска `scripts/notary-setup.sh` показывает, чего не хватает: сертификата «Developer ID Application»
в Связке ключей и профиля `notarytool`. Team ID берётся из сертификата (или `NEKTO_TEAM_ID`), в репозитории его нет.
Если Apple проверяет заявку долго, выпуск продолжает `scripts/release.sh --resume`.

Номер сборки — число коммитов, его ставит `build.sh`. На GitHub Releases выпуск выкладывает `scripts/publish.sh`:
образ, zip с приложением и `SHA256SUMS.txt` под тегом `v<версия>-<сборка>`, тег — на закоммиченный HEAD, который уже
есть на GitHub. Без аргументов — ad-hoc-сборка, пре-релиз с файлами `*-unsigned` и инструкцией, как разрешить запуск
в Системных настройках; `--notarized` выкладывает то, что собрал `release.sh`. `--draft` — черновик, `--dry-run` — только
файлы и описание в `build/publish.noindex/`.
